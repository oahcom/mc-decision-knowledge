# 知识库后续路线：评测驱动，而非数量驱动

本路线在 Amaidesu 接入和首轮 OFF/SHADOW/ASSIST 对照之后执行，不改变当前接入优先级。

## P0：先建立失败归因，不急着改知识

按失败签名聚类：目标、阶段、工具错误码、状态特征、命中知识、恢复方式、最终结果。每个问题只能归入以下一类主因：

- 知识缺失：没有可用策略或恢复卡片。
- 知识错误：结论、版本或适用条件错误。
- 检索错误：有好知识但未命中，或注入了无关知识。
- 状态错误：生命、背包、位置、任务进度等事实不可信。
- 工具错误：实际 MCP 行为与契约不符。
- 模型错误：知识正确但模型没有遵守。
- 评测错误：成功判定、种子或初始状态不一致。

禁止把所有失败都归因于“知识不够”。

## P1：修证据结构

- 将版本证明与内容证据分开；版本索引不能给玩法结论背书。
- 为关键结论建立 claim-to-source 对应关系，避免一条知识堆多个无关来源。
- 区分玩法事实、外部工具 API、Amaidesu 实际工具契约、项目策略阈值和 AI 启发。
- `evidence_strength` 等派生字段不得人工写成 high；由验证状态、证据和回放结果计算或删除。
- 所有策略阈值必须保持可配置，不得当成游戏规则。

## P2：小批量修复与回放

每批最多处理 5 条，只修最高频、最高损失且有日志证据的问题。先写最小复现，再改条目；同一失败场景通过后，还要在未参与修改的留出场景复测。

## P3：运行轨迹蒸馏

运行日志先进入候选经验区，不直接污染正式知识库。只有独立成功判定、可复现、版本匹配且经过回放的策略才可升级。模型自述、单次偶然成功、不同版本轨迹都不能单独成为高置信证据。

## 长期观测指标

- 检索命中率、注入后使用率、无关知识注入率。
- 每条知识关联的成功率、失败率、恢复率和负迁移次数。
- 重复失败率、重规划次数、tokens 与规划延迟。
- 知识版本过期率、草稿占比、回放覆盖率。
- OFF 与 ASSIST 的配对差异，而不是知识库条目数量。
